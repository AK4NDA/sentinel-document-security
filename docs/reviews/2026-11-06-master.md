## Major

### 🟠 ORM `session.delete(document)` fails with CircularDependencyError, `app/models/document.py:42-52`

**Problem**: `Document.versions` and `Document.shares` both carry `cascade="all, delete-orphan"`, while `documents.current_version_id` and `document_versions.document_id` form a bidirectional FK cycle (plus the `current_version` relationship at line 48). I reproduced this: `await session.delete(doc); await session.commit()` raises `sqlalchemy.exc.CircularDependencyError: Circular dependency detected. (_DeleteState(<Document>), _DeleteState(<DocumentVersion>))`. The DB-level `ON DELETE CASCADE` / `SET NULL` constraints are correct, but the ORM dependency processor walks the relationship graph and deadlocks on the cycle before it ever reaches the database.

**Why it matters**: Spec 0002 makes hard delete the document lifecycle (`documents`/`document_versions`: "a document is hard deleted (row removed, versions and shares cascade)"). Slice 1's delete endpoint will hit this on the most natural implementation path (`session.delete(doc)`). The existing tests only use the Core `delete(Document).where(...)` statement, which bypasses ORM cascade processing entirely, so nothing catches it.

**Suggested fix**: Since the database already enforces `ON DELETE CASCADE` on `document_versions.document_id` and `document_shares.document_id`, set `passive_deletes=True` on `Document.versions` and `Document.shares` (and keep or drop the ORM cascade accordingly) so the ORM does not try to load/cascade children it doesn't need to. Alternatively, document and enforce that document deletion always goes through a bulk `delete()` statement. Add a regression test that performs an actual ORM `session.delete(document)` + commit.

## Minor

### 🟡 Missing coverage for several spec critical scenarios, `tests/test_models.py`

**Problem**: With `TESTS = configured`, several branches of the contract are untested:
- `document_shares.user_id` ON DELETE CASCADE and `granted_by`/`revoked_by` ON DELETE RESTRICT are never exercised — only `sessions` user-cascade and `document_versions.created_by` RESTRICT are tested (`test_user_delete_cascades_sessions_but_restrict_blocks_authors`, which actually trips `documents.owner_id` RESTRICT first, not `created_by` specifically).
- `audit_log.id` uniqueness, `hash` NOT NULL, and `prev_hash` nullability are untested.
- AC-9's index set is asserted nowhere (a `PRAGMA index_list`/`pg_indexes` check or `alembic check` would cover it).
- The migration round-trip test only runs `downgrade -1` on SQLite; AC-1 requires clean upgrade/downgrade on Postgres too, and build-plan step 4 (`alembic check` / autogenerate drift) has no automated verification. The hand-written migration vs. model metadata drift risk is real even though I spot-checked names and they currently match.

**Why it matters**: These are exactly the failure/constraint cases the spec calls out as the contract (AC-4, AC-5, AC-6). A wrong `ondelete` on `document_shares` or a missing index would ship silently.

**Suggested fix**: Add tests for share cascade-on-user-delete and share RESTRICT on granter delete, audit_log uniqueness/nullability, and an index-presence assertion; run `alembic check` (or document why it can't run) against a migrated SQLite DB.

### 🟡 `audit_log.created_at` column is not in the spec sketch, `app/models/audit_log.py:38`

**Problem**: Spec 0002's `audit_log` sketch lists `occurred_at` but no `created_at`; the model and migration both add one (`sa.Column("created_at", ...)` at migration line 170). Harmless in isolation, but it is an undocumented schema divergence from the contract — either the spec or a comment should acknowledge it, since later slices will read this table.

**Why it matters**: Small, but this slice's entire value proposition is "schema is fixed once, correctly." An extra column nobody specified invites questions about which timestamp is authoritative (`occurred_at` vs `created_at`).

**Suggested fix**: Either drop the column or note in the model docstring/spec follow-up that `created_at` is an insert-time bookkeeping column distinct from `occurred_at`.

The audit log is append-only by convention so risk is low, and the spec explicitly chose this variant — just be aware `seq` is not gap/reuse-proof on SQLite the way `BIGSERIAL` is on Postgres.
