## [Unreleased]

### Added

- Project scaffold: FastAPI app shell, layered package layout (`app/api`, `app/core`, `app/models`, `app/repositories`, `app/schemas`, `app/security`, `app/services`), settings via `pydantic-settings`, structured logging, Alembic wired to SQLAlchemy async metadata.
- Core data model (spec `0002-data-model`), one Alembic migration creating seven tables:
  - `users` with role, classification clearance, active flag, login lockout counters, and encrypted TOTP fields.
  - `sessions` with hashed token storage, expiry, revocation, and client metadata.
  - `documents` and append only `document_versions` with per document version numbering, classification, content hash, storage path, and reserved key rotation columns.
  - `document_shares` with per user access levels and revocation tracking.
  - `audit_log`, an append only hash chained table storing actor and target as snapshots with no foreign keys so records survive deletes.
  - `alerts` with severity, dedup fingerprint, and acknowledgement fields.
- Model tests covering UUID defaults, uniqueness constraints, classification and outcome check constraints, cascade and restrict delete behavior, ORM level document delete, audit snapshot integrity, index presence, and an Alembic upgrade/downgrade round trip on SQLite.
- Core classified document loop (spec `0003-core-classified-document-loop`):
  - Authentication API under `/v1/auth` (`login`, `logout`, `me`) with opaque session tokens stored as SHA-256 hashes, HttpOnly SameSite cookies, Bearer token support, sliding expiry with a 24 hour absolute cap, revocation, and per request user re-reads so disabled accounts and role or clearance changes take effect immediately.
  - Admin user management under `/v1/users` (create officer and auditor accounts only, 12 character password minimum, audited) and a `python -m app create-admin` CLI bootstrap command with a hidden password prompt.
  - Document endpoints under `/v1/documents` for upload, list, metadata read, decrypted content download, new version, and hard delete, enforcing strict Bell LaPadula (no read up, no write down) and role rules (only the `user` role touches documents; admins manage accounts; auditors authenticate but reach nothing).
  - File uploads validated by size first (25 MB cap with a chunked reader that aborts early) then MIME allowlist, encrypted with AES GCM before storage at content addressed paths under `UPLOAD_DIR`, with classification pinned to the uploader's clearance and optimistic version conflict returning 409.
  - Real audit hash chain: canonical JSON SHA-256 entries with a 64 zero genesis `prev_hash`, a unique constraint on `prev_hash` plus bounded retry so concurrent writers cannot fork the chain, and a `verify_chain` helper that detects tampering. Every allowed and denied attempt after identity is established writes an entry in the same transaction as the business operation.
- MFA & login protection (spec `0004-mfa-login-protection`):
  - Mandatory TOTP enrollment for every role: `POST /v1/auth/mfa/enroll/start` returns the secret, an `otpauth://` URI, and an SVG QR code; secrets are stored AES GCM encrypted and `enroll/confirm` activates MFA after a valid code.
  - Two step login for enrolled users: password success returns `{mfa_required, pending_token, expires_in}` with no session cookie, and `POST /v1/auth/mfa/verify` exchanges the five minute pending token plus a TOTP code for a real session. Users without enrollment get a limited session that can only reach the enrollment endpoints, `/me`, and `/logout`.
  - New `mfa_challenges` table storing only SHA-256 token hashes with expiry, single active challenge per user, and a five bad code invalidation cap, plus `users.totp_last_counter` replay protection with plus or minus one step skew.
  - Account lockout shared across login, verify, and enroll confirm: five failed password or TOTP attempts lock the account for fifteen minutes with a 429 carrying `retry_after_seconds`, locked attempts never extend the lock, and the failure counter resets only when a full session is issued.
  - Admin recovery via `POST /v1/users/{id}/mfa/reset`, which clears the TOTP fields, revokes all of the user's sessions, deletes pending challenges, and is audited as `mfa.reset`.
  - `mfa_enrolled` on profile responses, `mfa.enroll`/`mfa.verify`/`mfa.reset` audit actions, enrollment gate denials audited under each endpoint's own action, and auth rate limits extended to the enroll and verify endpoints.
- Administration & account lifecycle (spec `0005-administration-account-lifecycle`), an admin control plane built on the existing session, lockout, and audit machinery with no new tables or migration:
  - `PATCH /v1/users/{user_id}` changes only `role` and `clearance` (admin only, MFA enrolled). Unknown fields, explicit nulls, an empty body, and out of range values return 422; setting a field to its current value returns 200 and is safe to retry. An admin cannot remove their own admin role (409 `self_demotion`). Audited as `user.privilege_update` with the old and new values of both fields.
  - `POST /v1/users/{user_id}/disable` and `POST /v1/users/{user_id}/enable` return 204. A disabled account fails validation on its next request and cannot log in, and disable deletes the target's pending MFA challenges so a login already past the password step cannot complete. Enable restores the account only: it does not clear the lockout and revives any unexpired, unrevoked sessions. Repeating the current state returns 409 (`already_disabled`, `already_enabled`), and an admin cannot disable their own account (409 `self_disable`). Audited as `user.disabled` / `user.enabled`.
  - `POST /v1/users/{user_id}/sessions/revoke` returns 204 and revokes every live session in a single UPDATE over `revoked_at IS NULL` and `expires_at` in the future, leaving expired sessions alone, with the count taken from the rowcount so it stays exact under concurrent logins. Audited as `session.revoke_all` with `revoked_count`.
  - `POST /v1/users/{user_id}/reset-password` returns 204, accepts `new_password` (12 to 256 characters), stores a new Argon2id hash, revokes all live sessions, deletes pending MFA challenges, and clears the login lockout so an active account can log in right away. It works on disabled accounts too and leaves MFA enrollment untouched (`mfa/reset` remains the only MFA reset path). Neither the password nor its hash appears in any response, log, or audit record. Audited as `user.password_reset` with `sessions_revoked` and `lockout_cleared`.
  - Every allow and deny event commits in the same transaction as the mutation through the hash chained audit log, with the actor stored as a snapshot and one action name per route for success, denial, and enrollment gate alike. Unknown user ids return an audited 404 `not_found`; officer and auditor calls return an audited 403. Role and clearance changes take effect on the next request without revoking sessions.
- Auditor access & log verification (spec `0006-auditor-access-log-verification`), giving the auditor role its own API surface with no schema changes:
  - `GET /v1/audit/entries` returns audit entries newest first (seq descending) with the full stored shape, filtered by `actor_username`, `action`, `outcome`, `target_type`, `target_id`, `occurred_after`, and `occurred_before` combined with AND, and paginated by a seq cursor (`next_cursor` is the last row's seq, null when no older entries remain; default page size 50, maximum 200). Entries are returned with their stored values, including corrupted ones, so tampering stays visible to the auditor. Routine list calls append no audit rows.
  - `POST /v1/audit/verify` recomputes the full hash chain synchronously and returns `valid`, `checked_count`, `head_hash`, and `bad_seq_numbers`. An edited middle entry flags its own seq; a deleted middle entry flags the successor row. `head_hash` and `bad_seq_numbers` describe the snapshot read before the call's own audit append, so they are unaffected by it; on an empty log the result is `valid` with a null `head_hash`. Every call appends exactly one `audit.verify` allowed row carrying `valid`, `checked_count`, and `bad_count`.
  - Both endpoints require the auditor role with completed MFA enrollment; admin and user calls get an audited 403 under the endpoint's action name (`audit.entries_list`, `audit.verify`), unenrolled auditors get an audited 403 `mfa enrollment required`, and auditor attempts on document endpoints remain denied and audited.
  - Verify is rate limited per session through the existing slowapi limiter, keyed on the SHA-256 of the session token with client IP fallback, driven by a new `RATE_LIMIT_AUDIT` setting defaulting to `30/minute`; `RATE_LIMIT_ENABLED=false` disables it and exceeding the limit returns 429.
- Document version history (spec `0007-document-version-history`):
  - `GET /v1/documents/{doc_id}/versions` lists every version newest first with number, classification, size, MIME type, content hash, creator, and timestamp.
  - `GET /v1/documents/{doc_id}/versions/{version_number}/content` downloads a historical version's decrypted bytes under the same read rules as the current version, and `POST /v1/documents/{doc_id}/versions/{version_number}/restore` appends a new current version copied from the source (content addressed blob reused, never duplicated) with its own audit row.
- Full text search over encrypted document content (spec `0008-full-text-search`):
  - `GET /v1/documents/search` requires every query term (case-insensitive, shared `casefold` + `\w+` tokenization) to appear in the union of the title, description, and extracted text of the current version, returning `DocumentMeta` rows plus `total`, `limit`, and `offset`.
  - Text is extracted once at upload, edit, and restore (PDF, DOCX, XLSX, PPTX, and `text/*` decoded as UTF-8 with replacement, capped at the first 2 MB) and stored only as AES-GCM ciphertext in the new nullable `document_versions.search_text` column; images and other non-extractable types stay searchable by title and description, extraction failures store NULL without failing the upload, and restore copies the source ciphertext or re-extracts when the source predates the feature. No plaintext derivative is persisted.
  - Candidates are filtered in SQL by non-null current version and caller clearance before any decryption, so results never reveal documents above the caller's clearance; per-document filtering is not separately audited, matching the `document.list` precedent. Every executed search appends one `document.search` allowed audit row carrying the truncated query and match total.
  - `q` is required (1 to 200 characters and must yield at least one token, else 422), `limit` defaults to 50 (max 200), `offset` defaults to 0, results order by `updated_at` descending with id as tiebreak, and an offset past the end returns an empty page while `total` still reports the full count. The endpoint is registered before `/{doc_id}` so `search` is never parsed as a document id, and carries its own `RATE_LIMIT_SEARCH` limit (default `30/minute`) wired through settings, `.env.example`, and `docker-compose.yml`.
- Per user document sharing (spec `0009-per-user-document-sharing`), owner managed read grants that let one named colleague read a document above their own clearance:
  - `POST /v1/documents/{doc_id}/shares` grants read access to an active `user` role account (self, disabled, admin, and auditor grantees are rejected with audited 409/404 denials), `DELETE /v1/documents/{doc_id}/shares/{user_id}` revokes, and `GET /v1/documents/{doc_id}/shares` lists every grant active and revoked with grantee, granter, revoker, and timestamps. Repeat grants are idempotent, regranting a revoked share reactivates the same row preserving `created_at`, and a grant that loses a concurrent insert race returns the winner's row on both SQLite and Postgres. Only the owner manages shares; everyone else gets the same non revealing 404 as a missing document.
  - An active share admits reads of the document metadata, current content, version list, and every historical version regardless of the grantee's clearance, while edit, delete, restore, and onward sharing stay owner and clearance gated. Allowed reads through a share append audit rows carrying `via_share` and `share_id`, recomputed inside the audit transaction so a mid request revoke cannot claim a dead share; grant, revoke, and share list calls are audited under `document.share_grant`, `document.share_revoke`, and `document.shares_list`.
  - `GET /v1/shares/mine` lists the caller's active shares newest first with title, description, current classification, owner username, and `shared_at`, audited as `document.list_shared`; shared documents never appear in `GET /v1/documents` or search results for the grantee.
  - `GET /v1/users/lookup` supports grantee selection with case insensitive prefix matching over active `user` role accounts (minimum 2 characters, `limit` 1 to 20 defaulting to 20, wildcard characters matched literally), returning only `{id, username}` and audited as `user.lookup`; it carries its own `RATE_LIMIT_USER_LOOKUP` limit (default `30/minute`) wired through settings, `.env.example`, and `docker-compose.yml`. Role, clearance, and disabled changes take effect on the next request while share rows persist.
- Maintenance & retention (spec `0012-maintenance-retention`), a scheduled cleanup that keeps tables and the upload volume bounded with zero operator effort:
  - `run_cleanup` in `app/services/maintenance.py` runs five independent stages per invocation: dead MFA challenges (consumed, expired, or attempt capped), dead sessions (expired or revoked), revoked document shares and acknowledged alerts past the retention window, and orphaned encrypted blobs. Each stage uses its own session and commits, a failing stage is logged and recorded in the report without aborting the others, and the run is idempotent so overlapping invocations race harmlessly.
  - Every run, including dry runs, appends exactly one `maintenance.cleanup` audit entry (`outcome=allowed`, `actor_username=system`) carrying per stage counts, the dry run flag, and any stage errors, so the cleanup itself is part of the hash chained audit trail.
  - `python -m app cleanup [--dry-run]` runs one pass from the CLI: dry run reports what each stage would delete without touching rows or files, stage errors print to stderr while the command still exits 0, and a chain fork exits 1.
  - An hourly in process scheduler starts in the app lifespan, runs once at startup then sleeps between runs, is guarded by a module level `asyncio.Lock` so in process runs never overlap, stops cleanly on cancellation, and is disabled entirely when `MAINTENANCE_INTERVAL_SECONDS=0`.
  - New settings wired through `.env.example` and `docker-compose.yml`: `MAINTENANCE_INTERVAL_SECONDS` (default 3600), `MAINTENANCE_SHARE_ALERT_RETENTION_DAYS` (default 90), and `MAINTENANCE_BLOB_MIN_AGE_SECONDS` (default 3600).
  - Blob collection scans two level shard directories for `*.enc` and `*.enc.tmp` files, deletes only files unreferenced by every `document_versions.blob_path` and older than the min age, tolerates a missing upload dir, and re-verifies each candidate (fresh reference query plus fresh mtime in a single thread call) immediately before unlinking; `blob_store.store` refreshes mtime on dedup hits so a blob claimed mid run is never collected.
- Audit log export (spec `0013-audit-log-export`), letting auditors pull a filtered slice of the audit log as a downloadable file:
  - `GET /v1/audit/export` streams the same filters as `GET /v1/audit/entries` (`actor_username`, `action`, `outcome`, `target_type`, `target_id`, `occurred_after`, `occurred_before`, all ANDed, inclusive time bounds) oldest first by `seq`, as `format=csv` (`text/csv`) or `format=json` (`application/x-ndjson`, one object per line); any other format returns 422 and paging params are not accepted.
  - Each export is pinned to the chain head captured at start (`seq <= head_seq`, `head_hash` of the tail row) via a shared filter builder so list and export cannot drift; the export's own `audit.export` row is appended after streaming and never appears in its own file, and concurrent exports committed before head capture can legitimately appear.
  - Output is capped by the new `EXPORT_MAX_ROWS` setting (default 50000, wired through settings, `.env.example`, and `docker-compose.yml`): a `COUNT(*)` probe over the same filters and snapshot bound decides truncation before headers are sent, truncated responses carry `X-Export-Truncated: true`, and rows stream through `session.stream()` with bounded memory.
  - Every allowed export appends one `audit.export` entry carrying the filters, format, `rows_exported`, `truncated`, `head_seq`, and `head_hash`; the append runs in a `finally` path on a separate transaction so client disconnects are still recorded with the partial row count, and empty results return a headers only CSV or empty JSONL body audited with zero rows.
  - CSV cells that could execute as spreadsheet formulas (leading `=`, `+`, `-`, `@`, tab, or carriage return, including after leading whitespace) are prefixed with a single quote; `details` serializes as compact sorted JSON in CSV and a nested object in JSONL. Exports require the auditor role with completed MFA enrollment, share the `RATE_LIMIT_AUDIT` per session limiter, and role denials are audited under `audit.export`.

### Fixed

- Argon2id password hashing and verification no longer run synchronously on the event loop; both go through `asyncio.to_thread`.
- Session sliding expiry now commits on read-only routes, blob writes are atomic via a temp file plus rename, blob hashing runs off the event loop, and the default plus audit rate limits are wired to the shared limiter (`RATE_LIMIT_DEFAULT` was previously dead config).
- Search audit fork retries no longer crash: response objects are built before the audit transaction opens, so a chain fork rollback cannot expire the ORM rows the retry reads.
